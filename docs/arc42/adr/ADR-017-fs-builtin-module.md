# ADR-017: Файловая система как встроенный модуль `fs` (промисы + `…Sync`, inotify через x/sys)

**Статус:** Принято, реализовано
**Дата:** 2026-08-24

## Контекст

Сценариям нужен доступ к файловой системе (sysfs, журналы, конфиги, временные файлы) без
`runShellCommand("cat …")`. Ранний вариант (PR #187, эпоха Duktape) добавлял **глобальный**
объект `fs` с callback-API в стиле Node.js, упрощёнными формами данных (`stat` со свойствами
вместо методов, `mode` строкой, ошибки только с `message`) и зависимостью `fsnotify` для
`fs.watch`. С переходом на QuickJS ([ADR-001](ADR-001-quickjs-instead-of-duktape.md)) и
промис-нативную библиотеку ([ADR-007](ADR-007-promise-native-lib-js.md)) требования изменились:
API должен быть `await`-ориентированным, типизированным ([ADR-013](ADR-013-type-system-wb-rules-dts.md))
и не должен засорять глобальное пространство имён.

## Решение

1. **Модуль, не глобал.** `require("fs")` / `require("fs/promises")` (и `node:`-варианты)
   разрешаются в `ModSearch` раньше каталогов модулей (как модули ядра Node.js). Тело модуля —
   `wbrules/fsmodule.js`, встроенный в бинарь (`go:embed`) и компилируемый **в realm каждого
   файла** (кэш `require` — per realm, [ADR-004](ADR-004-one-runtime-realm-per-file.md)):
   промисы, ошибки и классы `Stats`/`Dirent`/`FSWatcher` принадлежат требующему файлу, атрибуция
   после `await` сохраняется без дополнительных мер.
2. **Разделение JS/Go.** JS-слой: проверка аргументов, опции и их значения по умолчанию, формы
   результатов. Go-слой — четыре realm-локальных builtin'а: `_wbFsSync(op, args)`,
   `_wbFsAsync(op, args, cb)`, `_wbFsWatch(path, listener)`, `_wbFsWatchClose(id)`; операции —
   таблица `fsOps` чистых функций над уже проверенными аргументами, общая для обоих входов.
   Асинхронный вход повторяет жизненный цикл `spawn`: горутина → `MaybeCallSync` → однократный
   вызов колбэка в cleanup-scope файла, немедленный sweep stash-записи, `noteOrphanedCallback`
   при остановленном движке.
3. **Формы данных — Node-точные.** `Stats` с методами `isFile()`/…, числовым `mode`, `*Ms` и
   `Date`-полями; `readdir` → имена или `Dirent` при `withFileTypes`; ошибки `Error` с
   `code`/`errno`/`syscall`/`path`/`dest` и Node-сообщением; `TypeError` с
   `ERR_INVALID_ARG_TYPE`/`ERR_INVALID_ARG_VALUE` для неверных аргументов. Сознательные
   отличия: только строки UTF-8 (без `Buffer`), только промисы (без колбэков; `fs.readFile ===
   fs.promises.readFile`), `exists()` как промис, `watch` без EventEmitter, лимит `readFile`
   10 МиБ, нет дескрипторов/потоков.
4. **`fs.watch` напрямую поверх inotify(7)** через `golang.org/x/sys/unix` (уже зависимость той
   же версии, что у плагина `wbgo.so`): один inotify-дескриптор на watcher, горутина-читатель,
   маска как у libuv (число событий совпадает с Node), доставка слушателю через `MaybeCallSync`.
   Watcher закрывается cleanup'ом файла, `Stop()` движка, `close()` из JS и при `IN_IGNORED`
   (удаление наблюдаемого пути) — все пути сходятся в идемпотентном `close()`.
5. **TypeScript.** Декларации `declare module "fs"`/`"fs/promises"` в `wb-rules.d.ts`,
   перегрузки `require("fs")`. Чтобы `import * as fs from "fs"` работал в `.ts`-сценариях,
   транспилятор переведён на `module: CommonJS` + `esModuleInterop` (ESM-синтаксис внутри
   `async function F(module, exports)` был бы `SyntaxError`); фоновая проверка получила
   `--esModuleInterop`. Побочный эффект: `export` в `.ts`-сценариях тоже начал работать.

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Глобальный объект `fs` (как в #187) | засоряет глобальное пространство всех сценариев; конфликтует с пользовательскими переменными `fs`; непривычно для TS (`import`) |
| Callback-API + `fs.promises` (1:1 с Node) | двойная поверхность и типы; библиотека wb-rules промис-нативна ([ADR-007](ADR-007-promise-native-lib-js.md)); колбэки при желании получаются из промисов, обратное — нет |
| Гибрид (колбэк, если последний аргумент — функция) | неявная семантика, усложняет типы и `throwIfNoEntry`-подобные перегрузки |
| `fsnotify` для `watch` | новая зависимость с иной версией у `wbgo-private` — риск несовпадения пакетов при `plugin.Open` (плагин проверяет версии общих пакетов); inotify напрямую — ~200 строк без зависимостей |
| Опрос `stat` вместо inotify | задержка и нагрузка на медленных носителях; события не различимы |
| Бинарные данные через `Uint8Array` | нужна поддержка typed array в шиме ([ADR-003](ADR-003-go-duktape-compatible-shim.md): поверхность заморожена); отложено до реального запроса |
| Реализация целиком в Go (без JS-слоя) | ручные promise capabilities и повторный вход в правильный realm — тот же класс багов атрибуции, что отклонён в ADR-007 |
| Песочница путей / запрет записи в системные каталоги | `spawn()` уже даёт неограниченный доступ; ограничение создало бы ложное чувство безопасности; задокументировано как «права процесса» (§8.9) |

## Последствия

Плюсы:
- Знакомый API: документация Node.js применима с оговорками из README; типы дают подсказки в
  редакторе и проверку на контроллере.
- `import`/`export` в TypeScript-сценариях (ранее любой `import` ломал загрузку файла).
- Никаких новых зависимостей и никакого влияния на ABI плагина `wbgo.so`.

Минусы и риски:
- Синхронные операции блокируют engine loop (как `readConfig`): задокументировано, для
  больших/медленных операций — асинхронные версии.
- Один inotify-дескриптор на watcher: лимит `fs.inotify.max_user_instances` (обычно 128) —
  практически недостижим для сценариев, но не проверяется заранее; ошибка `EMFILE` при
  создании.
- `GetJSObject(idx)` конвертирует только вершину стека (латентная особенность шима): builtin'ы
  с колбэком поверх массива аргументов должны дублировать аргумент на вершину (`fsOpArgs`).
- Преамбула interop-хелперов в CommonJS-выводе сдвигает строки сгенерированного кода —
  source-map таблица это учитывает (закреплено тестом `TestTsFsErrorLineNumbers`).

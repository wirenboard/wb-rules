# ADR-002: Bellard QuickJS 2026-06-04 как git-submodule (не quickjs-ng, не vendored-копия)

**Статус:** Принято, реализовано (форк в org wirenboard — предложено, не создан)
**Дата:** 2026-08-13

## Контекст

Debian поставляет QuickJS 2025-04-26 — не последний релиз, а проект существует в двух ветках:
эталонная реализация Беллара (официальный репозиторий на GitHub и официальный сайт) и форк
quickjs-ng. Нужно было выбрать (а) какую ветку брать, (б) как поставлять исходники в репозиторий
wb-rules так, чтобы работала cgo-кросс-сборка armhf/arm64 и Debian-упаковка, и при этом версия
движка была актуальной и точно воспроизводимой.

## Решение

- `third_party/quickjs` — git-submodule `https://github.com/bellard/quickjs`, закреплённый на
  коммите `3d5e064e9dd67c70f7962836505a7fa067bf0a4e` = релиз 2026-06-04 (байт-в-байт совпадает с
  официальным tarball). Upstream не модифицируется.
- Если патчи всё же понадобятся — создать форк в организации wirenboard и переключить
  `.gitmodules` на него; диффы против upstream остаются видимыми как история репозитория.
- Сборка без Makefile-шага и без системной библиотеки: в `internal/quickjsduk/` лежат пять
  однострочных обёрток `qjs_build.c`, `qjs_cutils.c`, `qjs_dtoa.c`, `qjs_libregexp.c`,
  `qjs_libunicode.c`, которые `#include` исходники из сабмодуля (cgo компилирует только `.c`,
  лежащие в каталоге пакета). Дополнительно `#pragma GCC optimize("wrapv")` (cgo фильтрует
  `-fwrapv`) и `#define CONFIG_VERSION "2026-06-04"`; CFLAGS `-I${SRCDIR}/../../third_party/quickjs`.
- Кросс-сборка armhf/arm64 — штатный `CC=arm-linux-gnueabihf-gcc` / `aarch64-linux-gnu-gcc`.

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| quickjs-ng v0.16.1 | более частые релизы, CMake, perf-работа — но это форк с собственной дорожной картой; эталонная реализация Bellard предпочтительнее как референс спецификации и источник апстрим-исправлений |
| Vendored-копия (5 `.c` + ~10 `.h`, 2.6 MB) со скриптом sync + sha256 | так поставлялся go-duktape; проще кросс-сборка и deb. Отклонена: submodule с пином на репозиторий Беллара проще сопровождать и сравнивать с upstream, если понадобятся патчи |
| Debian-пакет `libquickjs` | версия 2025-04-26 отстаёт; зависимость от дистрибутива; нет на armhf-стендах в нужной версии |
| Системная библиотека + Makefile-шаг | лишний этап сборки, ломает `go build ./...` из чистого клона |

## Последствия

Плюсы:
- Точная, проверяемая версия движка; обновление = bump сабмодуля + `CONFIG_VERSION`.
- `go build` / `go test` работают из клона без внешних шагов.
- Путь для патчей ясен (форк + смена URL сабмодуля), история diff'ов не теряется.

Минусы и риски:
- У Bellard нет git-тегов релизов — соответствие хеша релизу сверяется вручную.
- `git clone` обязан быть `--recursive`; на CI это взаимодействует с приватным сабмодулем корпуса:
  `update = none` у корпуса — иначе клон падает и оставляет `third_party/quickjs` пустым.
- `CONFIG_VERSION` надо обновлять синхронно с сабмодулем (иначе неверная строка версии движка).
- Форк wirenboard/quickjs не создан (нужны права в org) — на момент написания патчей не требуется.
- Codacy/CVE-сканеры видят C-исходники — `.codacy.yml` исключает `third_party/`.

### Риски и технический долг

- Риск: у Bellard нет git-тегов — пин по хешу сверяется с релизом вручную, `CONFIG_VERSION` обновляется отдельно, `git clone` без `--recursive` даёт пустой каталог (предлагается скрипт «хеш ↔ sha256 tarball» и тест на `CONFIG_VERSION`).
- Риск: форк `wirenboard/quickjs` не создан (нужны права в org) — при первом же патче придётся решать, где его держать.
- Шум Codacy/CVE-сканеров по C-исходникам — `.codacy.yml` исключает `third_party/`; принято как есть.

# 1. Введение и цели

## 1.1. Обзор задач

**wb-rules** — движок правил автоматизации контроллеров Wiren Board (WB6/WB7 на armhf,
WB8 на arm64). Это один Go-процесс (`/usr/bin/wb-rules`, systemd-сервис `wb-rules`),
который:

- загружает файлы правил `/etc/wb-rules/*.js|*.ts` (а также системные правила
  `wb-rules-system`, `wb-scenarios` и модули из `/etc/wb-rules-modules`,
  `/usr/share/wb-rules-modules`), следит за их изменением и перезагружает «на лету»;
- подписывается через MQTT-брокер на все контролы устройств (`/devices/+/controls/+`)
  и по событиям изменения вызывает правила (`whenChanged`, `when`, `asSoonAs`, `cron`,
  таймеры); отслеживание зависимостей (`DepTracker`) выбирает, какие правила пересчитать;
- публикует собственные виртуальные устройства (`defineVirtualDevice`), пишет в контролы
  внешних устройств (`/on`), выполняет внешние команды (`spawn`, `runShellCommand`),
  рассылает уведомления (`Notify`, `Alarms`), хранит состояние (`PersistentStorage`);
- предоставляет редактору homeui MQTT-RPC `wbrules/Editor` (список, загрузка, сохранение,
  переименование, включение/выключение, проверка типов, выдача `.d.ts`) и поток лога
  `/wbrules/log/+` для консоли отладки.

Подробное описание API правил — в [README.md](../../README.md) репозитория.

## 1.2. Цели качества

Приоритеты (1 — высший); сценарии и измеренные значения — в [§10](10-quality-requirements.md).

| # | Цель качества | Кратко | Сценарии §10 |
|---|---|---|---|
| 1 | Совместимость со старыми ES5-правилами | файл, работавший на Duktape, загружается и ведёт себя так же; системные скрипты `wb-rules-system`/`wb-scenarios` не меняются | Q1–Q2 |
| 2 | Отзывчивость и низкое потребление RAM | RSS не выше Duktape-версии, реакция MQTT → правило в единицах мс, `.ts` не задерживает запуск | Q3–Q6 |
| 3 | Устойчивость к сбойным правилам | бесконечный цикл, allocation bomb, падение при загрузке одного файла не валят и не вешают остальные | Q7–Q11 |
| 4 | Ранняя и видимая диагностика ошибок | ошибки типов до запуска, ошибки после `await` и отклонённые записи в контрол — в логе и редакторе с `file:line` | Q12–Q15 |
| 5 | Современный язык и типы без внешних инструментов | ES2025+, TypeScript с проверкой на контроллере и в web-редакторе, без Node/webpack на ПК | Q16–Q18 |

Неявные цели из ограничений (§2): одно-процессная модель, поставка deb-пакетами, без второго рантайма (Node) на контроллере.

## 1.3. Заинтересованные стороны

| Роль | Кто | Ожидания от архитектуры и документации |
|---|---|---|
| **Интеграторы** (профессиональные инсталляторы, основной «шумный» сегмент чата и книги жалоб) | авторы крупных наборов правил, часто с TS-компиляцией в ES5 на ПК | стабильность на объекте (на wb-rules возлагают ответственный функционал), изоляция ошибок одного файла, читаемые ошибки с `file:line`, типизация `dev["d/c"]`, HTTP/API без `curl`-приседаний (последнее — вне этого этапа) |
| **Продвинутые TS-пользователи / сообщество wb-mirta** | авторы и пользователи фреймворка wb-mirta, `@mirta/globals` | штатный TS на контроллере, совместимость идиом (файл `.ts`, `defineRule` со стрелками, `import`-стиль — пока CommonJS), d.ts, который можно использовать в VS Code; ожидали «wb-rules 3.0 на nodejs» — получили QuickJS+tsgo с тем же языковым уровнем |
| **Новички** (в т.ч. пишущие правила с помощью ИИ) | пользователи web-редактора homeui | подсказки и подчёркивания в редакторе, ошибки «сразу при сохранении», отсутствие ES5-ловушек (`let`, `replaceAll`, `find` теперь работают), понятные сообщения вместо `duk_js_executor.c:2761` |
| **Техподдержка WB** | support.wirenboard.com, книга жалоб | меньше «перезапустите wb-rules» как лекарства; диагностика через `journalctl` и консоль правил (`TS check:`, `write ignored`, `[loadguard]`, `execution timed out`) |
| **Разработчики WB (wb-rules, homeui, wbgo-private, wb-tsgo)** | команда ПО Wiren Board | понятные границы: шим «заморожен», новые API — в `lib.js`; где лежат ADR; как собрать и протестировать (`wbgo.so` тем же toolchain, корпус локально); стратегия stacked PR |
| **wb-scenarios / wb-rules-system** | системные скрипты, поставляемые пакетами | обязаны оставаться ES5 до снятия stable 2.46.x с Duktape; их предупреждения `checkJs` исправлены в PR wb-rules-system #65 и wb-scenarios #98; `Breaks:` в `debian/control` на старые версии |
| **homeui** | фронтенд контроллера | стабильный RPC `Editor.Check/GetTypes`, `/wbrules/log/+`, `/wbrules/updates/+`; деградация на старом движке (`Recommends: wb-rules (>= 3.0.0~~)`) |
| **Эксплуатация / безопасность** | администраторы контроллеров | лимиты памяти (`JS_SetMemoryLimit`, systemd `MemoryMax`), права `0640` на persistent DB, отсутствие секретов в логах; Prometheus `/metrics` за `-http` |

Обратная связь от пользователей (чат сообщества, книга жалоб, портал техподдержки, трекер
задач) даёт устойчивый набор повторяющихся тем: устаревший ES5;
«одно правило вешает всё»; невидимые ошибки; редактор без проверки и автодополнения;
HTTP только через `curl`. Этот этап закрывает первые четыре; HTTP/fetch, ES-модули,
история данных и редактирование модулей в web остаются в roadmap (§9, «Что сознательно не решено»).
